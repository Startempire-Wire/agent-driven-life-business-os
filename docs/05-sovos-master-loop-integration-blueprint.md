## 1. Purpose and interpretation

Make the agreed organism sufficiently precise that a builder cannot invent the missing joins. This annex owns proposed cross-product behavior, not another Golden Path, scheduler, database, compiler, ontology or authority. Current product contracts remain controlling. The owner's request authorizes refinement of this draft; promotion into canonical product contracts and execution remain separate.

The [modular blueprint](08-sovos-master-loop-modular-composition-and-evolution-blueprint.md) specializes these same obligations for capability/profile/version linking, typed hooks, dependencies, lifecycle, provider replacement and multi-axis upgrades. It uses the existing owners/registries/compiler/control boundaries, not a new kernel, module service or requirement registry. Stable capability contracts separate from implementation/binding/instance/state generations; current grants are never inherited by a swap. Memory's exact future plug-in agreement stays provisional under its owning blueprint.

Requirement IDs below identify design/acceptance obligations, NOT tasks, CallGraph nodes or ready work. Operation labels are logical signatures, NOT registered APIs, routes, tool names or new schemas. A product binding must map them to verified existing operations or an explicitly accepted extension before decomposition.

Paper completeness means an agreed finite boundary, explicit responsibility, precise transitions and testable acceptance. It does not mean all code already exists or customer-private IDs/secrets must be filled into a shared document. Distinguish unresolved architecture/contract semantics from deliberately parameterized deployment values: specify their owner, type, bounds, verification and missing-value behavior; bind actual private values later through the approved compiler. Unsupported seams receive an accepted extension/exclusion design; inaccessible sources remain unverified. A draft revision, a schema-valid string or an open issue cannot supply runtime proof.

## 2. Proposed responsibility assignment

This revision proposes a concrete allocation instead of leaving every alarm owner unnamed. These allocations require review against the controlling architecture and actual product contracts; they are not self-promoted authority.

| Object / responsibility | Proposed canonical owner | Cross-product boundary |
|---|---|---|
| Commitment, due condition, cancellation, actual business/life state | Existing source domain or explicitly owner-accepted commitment | Other systems hold refs, not competing domain truth |
| Source observation, cursor and coverage | Owning source adapter | Preserve account, revision, uncertainty and read scope |
| Concern/thread correlation and continuity projection | Wirebot's existing Operating Partner/Perpetua product state | Minimal source refs, relation proposals, responsibility and next-check refs; no second CRM/task/outcome store |
| Accepted expectation definition | Source/commitment owner | Wirebot links a watch to its revision; an inferred watch stays labeled and cannot invent a deadline |
| Watch/trigger execution | Existing source-native scheduler where stronger; otherwise OpenClaw durable automation | Wirebot stores only the binding ref; scheduler owns timer/run state |
| Assignment, grants, leases, governed execution and work settlement | Focusa plus the actual task/worker/executor owners | Do not manufacture reducer state from Wirebot or reinterpret a provider task as accepted outcome |
| Semantic judgment | Existing bounded-cognition/Decision-family adapter | Source-minimized advisory result; no authority, case writer or model-specific store |
| Notification/reply presentation | Wirebot/OpenClaw channel adapters under attention policy | Seen/snoozed/delivered is not source resolution or approval |
| Receiver acceptance and business/life outcome | Source/receiver plus required human acceptance | Evidence refers to independent observation, not only executor report |
| Episode review, delivery, recall, correction and retention | Existing memory owners | Current eligibility and role boundaries; no parallel gut-memory store |
| Health, recovery, learning and leverage | Existing health systems, Focusa epistemic owners, Wirebot synthesis | Fault recovery and learned revisions stay inside actual grants |

**ML-OWN-01:** the concern projection may persist only information it owns: scoped correlation identity, source-qualified links, projection revision, relation/uncertainty disposition and continuity metadata. Source facts, tasks, grants and accepted outcomes stay elsewhere. Exact existing Wirebot persistence and consumer operations remain a binding gate; this table does not authorize a new database.

**ML-OWN-02:** an authenticated explicit owner instruction can itself supply accepted expectation intent. Bind its durable source revision, exact target/time and correction/cancel authority through existing capture/conversation and watch owners; use a native task/calendar/provider record only when the actual domain requires one. Focusa Temporal Authority represents time within its applicable scope. Missing attribution, acceptance or durable binding leaves authoritative absence unavailable. This [responsibility resolution](06-sovos-master-loop-contract-and-policy-resolution.md) creates neither a compulsory task for every reminder nor a Wirebot commitment database or model-inferred deadline.

### 3.1 Semantic linking and reproducible compilation

**ML-COMP-01:** validate shape, then resolve each template, blueprint, operation, input/output schema, decision policy, prompt, attention policy, assignment, credential-use, retry, revoke and acceptance ref through its owner. Record exact version/revision/digest, scope and support disposition. A nonempty string is not a successful link.

**ML-COMP-02:** compilation fixes all approved semantics: purpose/outcomes, scope, step identity/order/dependencies, operation and argument bounds, input/output/error types, model question/prompt policies, consequence/effect classes, confirmation/handoff, verification, compensation, reliability, trigger, privacy and revision lineage. Use the owning canonical serialization/digest mechanism, not ambiguous concatenated strings or a new hashing convention.

**ML-COMP-03:** artifact identity and execution authority are different. Freeze approved semantic refs in the instance; resolve current validity/revocation/expiry at every effect boundary. A grant's stale bytes cannot remain operative because they were included in a compilation digest.

**ML-COMP-04:** SOVOS `deterministic/agentic/uiai/human` step kinds and `read/prepare/mutate/external_commitment/human_reserved` consequences are not one-to-one aliases of Focusa `shell/api/agent/human_handoff/approval` and its effect classes. Derive an explicit reviewed mapping from actual operation effects. Unknown mapping blocks the affected step; destructive/financial/security confirmation requirements cannot be downgraded by an adapter.

**ML-COMP-05:** semantic judgment answers bounded questions; response drafting is a different step with its own output/offer/privacy contract. A typed Jev choice cannot satisfy a free-text preparation contract. Missing required outputs stop dependent work; optional outputs require an explicit fallback.

**ML-COMP-06:** each accepted material change creates a new proposed/accepted instance revision. Do not alter an active instance in place. Migration declares old-run drain/fence/reconcile, trigger replacement, case/watch continuity, logical-effect deduplication, rollback limits and old/new consumer compatibility. Template changes alone do not trigger migration. Modular §§5–8 defines dependency/exclusive-role linking, lifecycle, old callback routing, state versus code rollback and compatible-read/shadow/canary/drain/state-migration methods for the chosen upgrade dimension.

### 3.2 Source qualification concerns

Inspected Focusa core already contains `procedure_compiler::compile_plan`, confirmation/handoff flags, reverse rollback order and unit-test source. Its Spec 167 document remains design-stage; neither proves a complete running compiler. The reviewed digest uses procedure ID, step IDs and commands but omits other material semantics. Before that digest identifies an approved executable artifact, prove that version/effect/kind/confirmation/rollback changes affect identity, and distinguish different structured inputs with the same concatenated bytes.

The inspected CallGraph API has settlement code absent from an older implementation inventory. These findings were rechecked against published Focusa `b10c605e1e0ccbdb43d9650945adde7a87fec25d`, not only the older local checkout: `procedure_compiler.rs` retains the digest coverage described above; `callgraph_store.rs::mark_dispatch_settled` stores receipts but discards its outcome argument; `routes/callgraph.rs::settle_frame` can mark a run completed before adding failed-settlement compensation dispatches. Dispatch rows/leases/events alone do not prove adapter execution. Qualification must preserve outcome and prevent completion while required verification, branches or compensation remain unsettled.

These are source-level findings, not newly executed regressions or production-exploit claims. Remedies and tests belong to the existing procedure/CallGraph programs; this draft neither patches them nor creates another execution authority.

## 4. Logical integration operations and record requirements

No field below is a newly installed enum/schema. Map the semantic requirements to the product's exact contract, preserving unsupported/denied/unavailable dispositions.

| Logical signature | Preconditions | Postcondition / failure behavior |
|---|---|---|
| `Observe(source, cursor, read_scope)` | Exact account/tenant, permitted fields, supported source version | Source-bearing observation plus coverage/cursor; failed read is unavailable/denied, not empty |
| `BindWatch(commitment_revision, condition, calendar, policy, instance)` | Accepted origin, exact predicate/window and trigger owner | Durable source-linked watch ref or blocked binding; no deadline generated from recurrence |
| `ProjectConcern(observation_refs, expectation_ref, expected_case_revision)` | Scope-compatible inputs, known coverage, existing-case lookup | Compare-and-update or conflict; original evidence preserved; model relation remains proposed until validated |
| `Enrich(question_policy, information_set, subject_revision)` | Applicability, permitted route/disclosure, budget, valid source snapshot | Advisory result with exact provenance or rejected/abstained/unavailable; no case/effect mutation |
| `ReconcileAssignment(case, existing_work, actor_capacity)` | Live incumbent responsibility and actual assignee identity | Existing work reused, accepted new handoff or explicit wait/decline; no duplicate unaccepted assignment |
| `AdmitAttempt(instance, inputs, current_grants, generation)` | Resolved versions, lease, budget, source freshness, consequence and verifier availability | Exact permitted attempt or non-admission; no dispatch-success claim from a queue/ledger insertion |
| `ExecuteIntent(logical_effect, expected_source_revision)` | Current permission, argument bounds, idempotency/reconciliation, required confirmation | Provider/executor receipt or partial/unknown state; unknown effect blocks blind retry |
| `VerifyOutcome(outcome_policy, receipt_refs, receiver_refs)` | Independent current receiver/source evidence under permitted read scope | Accepted/failed/partial/disputed/unknown result; task completion alone cannot settle |
| `ContinueOrClose(case_revision, outcome, momentum_policy)` | Exact result and terminal/horizon policy | Source-backed close/supersede/escalate or bounded next-check binding; no indefinite activity quota |
| `SubmitEpisodeOrCorrection(source_refs, eligibility_policy)` | Actual review/retention owner, minimal purpose-scoped payload | Reviewable candidate; accepted revision and sink delivery remain separate operations |
| `InvalidateDerivedContext(correction_revision, dependency_refs)` | Verified correction/current eligibility and affected-scope lookup | Dependent pending context made stale and re-observed; completed effects are not automatically undone |

Common semantic requirements: namespace/object/account/principal/domain refs; producer and schema revision; source revision/cursor/generation; observation versus inference; coverage/freshness/expiry; correlation and causal predecessor; recipient/purpose/retention; supported error class; replay/effect identity; relevant assignment/instance/lease generation; evidence and acceptance refs. Only required minimal fields cross a boundary. Secret refs do not carry secret values.

**ML-LINK-01:** entity matching is source-qualified. Equal names, amounts or bare IDs do not prove one entity/event. Ambiguous matches remain proposed; a reversible split preserves source identity, responsibility and past effect intents. Use existing semantic-graph verification/promotion mechanisms where supported, not model agreement.

**ML-LINK-02:** correlation identity tells the causal story; it is not the idempotency key, source revision, authorization token or object owner. One concern can contain several distinct legitimate effects; a merged/split concern must not reset provider deduplication.

## 5. Expectation, concern and attention lifecycles

### 5.1 Explicit expectation

**ML-WATCH-01:** bind origin/acceptance, source commitment revision, expected event/state predicate, source coverage, due window, grace if actually authorized, business calendar/timezone/DST, readiness/check policy, cancellation/supersession and terminal conditions. Check time, estimated response likelihood and authoritative due time remain distinct.

| Expectation disposition | Transition condition | Permitted behavior |
|---|---|---|
| Proposed | Inferred pattern or draft commitment | Review/watch proposal only; not authoritative overdue |
| Bound / watching | Accepted origin and supported persistent binding | Event observation plus scheduled reconciliation under the named owner |
| Not yet due | Current predicate absent but valid window not elapsed | Quiet monitoring; no false overdue |
| Satisfied | Current source evidence meets predicate | Stop obsolete due checks; proceed to independently defined outcome/momentum |
| Possibly absent / coverage unknown | Window reached but required evidence is incomplete | Preserve concern, diagnose/wait/escalate as permitted; no duplicate outreach based on assumed silence |
| Absent | Window elapsed, sufficient source coverage, exceptions reconciled | Existing permitted response or bounded preparation/Needs You |
| Cancelled / superseded / paused | Current authoritative change | Disarm/fence affected future work; preserve history and reconcile pending effects |
| Disputed | Conflicting source/attribution | No consequential transition depending on contested truth until owning resolution |

**ML-WATCH-02:** installing a trigger must be verifiable and associated with one exact instance/watch revision. Binding failures do not leave a fictitious active watch. Reconnect uses the scheduler/source cursor, rechecks current commitments and inspects effects before catch-up. Calendar or policy changes require reviewed recomputation; they cannot silently extend a deadline.

**ML-WATCH-03:** monitor watch health separately from business condition: last successful source read, coverage interval, source cursor, last admitted check and next supported check. Healthy silence, stale watch and disconnected source are distinct. Reuse existing scheduler/health mechanisms; do not recursively create a watchdog agent for every watchdog.

### 5.2 Concern projection and responsibility

| Concern disposition | Guard / transition | Required continuity |
|---|---|---|
| Candidate | Meaningful observation or expectation deviation | Evidence, uncertainty and exact scope |
| Watching | No warranted action currently due | Named next event/check and expiry/terminal policy |
| Reconciling / investigating | Evidence conflict or bounded uncertainty | Current inputs, inquiry budget, responsible owner |
| Action due / prepared | Accepted policy warrants an allowed next move | Existing work lookup, effect intent and authority boundary |
| Assigned / external wait | Real actor accepted, or provider response genuinely pending | Acknowledgement/source ref, responsibility, next check |
| Needs You / blocked | A precise missing truth, permission, capacity or unsupported capability | One source-bearing item; affected work fenced, independent permitted work may continue |
| Verifying | Effect occurred or task reports completion | Receiver predicate, independent evidence and unresolved contradictions |
| Follow-through | Outcome accepted; relevant next state still being evaluated | Bounded horizon, hypothesis, owner fit and honest unknown momentum |
| Closed / superseded / escalated | Accepted terminal predicate reached | Closure evidence and destination; unresolved source obligations never hidden by UX dismissal |

**ML-CASE-01:** every nonterminal concern identifies its responsible owner and next useful event/check or explicit blocker. An unreadable queue, failed lookup or missing assignee is not empty work. Repeated unchanged readings update continuity rather than spawn cases/tasks.

**ML-CASE-02:** reopening requires a material source revision or accepted policy condition. False merges are reversible; suppression states retain reason, scope, expiry and recheck. Quiet hours alter presentation, not source truth or current permissions.

**ML-ATTN-01:** acknowledge/snooze/read clears only presentation. Attributed owner replies revalidate current concern/source revision, exact target and consequence scope. Speech uncertainty cannot become a new binding or destructive action. Delivery failure preserves the obligation and uses only a permitted fallback.

## 6. Jev / local judgment contract

**ML-JUDGE-01:** reuse routine `decision_policy_ref` / `prompt_contract_ref` and existing Decision-family mechanisms. No Jev-specific routine schema or second decision registry. Exact adapter and fields require owning-contract binding.

A question freezes: narrow purpose and policy revision; finite labels/range; applicability/exclusions; minimized evidence refs and source revisions; subject/concern/instance/steering revision; permitted route/model version and residency; deadline/expiry; result/input budgets; validator; allowed consequence ceiling; abstention/escalation; independent outcome-resolution/evaluation policy.

A result retains: request/question/information-set identity; provider/model/method revision; typed answer; distributions/confidence only if actually supplied; validation/error/abstention; elapsed transport/queue/inference and cost; expiry and evidence lineage. Concentration is not calibrated correctness. Jev's hosted route and a local model are separate disclosure policies, not interchangeable fallback hosts.

| Processing point | Required rule |
|---|---|
| Before request | Deterministic scope/freshness/adversarial-data/applicability checks; mechanical questions use code |
| While pending | Initial signal admission and necessary exact reflexes continue; optional work is bounded and cancellable |
| On arrival | Validate shape/policy and re-resolve current subject/source/assignment/steering; stale answers cannot change current routing |
| On duplicate/cache hit | Same exact scope, policy, model and eligible input revisions; cache validity does not waive live revalidation |
| On failure | Preserve unresolved concern and original failure; use allowed deterministic path, abstain or escalate |
| On proposed action | The owning policy, current grant and source preconditions admit it independently; model confidence supplies no authority |

**ML-JUDGE-02:** Kai remains the preferred local candidate, Jev a permitted managed comparison/optional route; no permanent model binding is selected. Local unavailability never discloses private inputs externally by default. Ordinary failed judgment cannot turn a speculative concern into a severe alarm merely through repeated retries.

**ML-JUDGE-03:** calibration uses held-out matched rules-only, rules+model and warranted-specialist cases, including abstention, wrong high confidence, choice order, contradictory criteria, languages, source outages and adversarial text. Select consequences/thresholds from the approved error-cost policy; no universal confidence cutoff. Test consumer behavior, not merely model answer accuracy.

## 7. Assignment, resource and effect coordination

**ML-TEAM-01:** reconcile source work and incumbent employee/manager/VA responsibility before new dispatch. A human handoff is offered then accepted/declined/unacknowledged through the actual provider; a role label is not acceptance. Acknowledgement windows must be explicitly bound, not invented from silence. Reassignment reconciles pending effects and fences the prior generation before another actor acts.

**ML-TEAM-02:** separate contributing actor from accountable owner and independent verifier. Worker availability, read access, effect permission and verifier independence are checked separately. Replacements receive only role-purpose-scoped context; no inherited ambient credentials or partner-wide memory.

**ML-EFFECT-01:** identify an intended effect by exact scope, source subject/commitment, operation, target and accepted semantic intent. Preserve its owning idempotency identity across retries, worker replacement, reconnect and compatible instance migration. New attempt/run/worker/template revision must not automatically create a new provider key. A genuinely new follow-up/action needs a distinct accepted intent after prior effects are reconciled.

**ML-EFFECT-02:** before competing work proceeds, use owning conditional revisions/leases/reservations to resolve the same effect, source object or exclusive resource. No distributed all-product transaction is assumed. Persist intent/admission before dispatch where supported; provider receipt and local record may complete separately. A missing local receipt requires source/idempotency reconciliation, not repetition.

**ML-EFFECT-03:** compensation applies only to verified completed/partial effects under current authority and current source preconditions, in the actual permitted reverse dependency order. A declared rollback for a never-executed step is not due work. Irreversible communications, financial reversals and residual risks require their actual policies/acceptance; cancellation or compensated status cannot mean the original desired outcome succeeded.

**ML-RESOURCE-01:** bind per-instance and shared limits for event buffers, concurrent attempts/models/specialists, source API rate, retries, wall time, money, CPU/memory and notification/owner attention. Hard caps are enforced by the actual owner. Missing mandatory limits block the corresponding optional workload; exhaustion does not self-renew.

**ML-RESOURCE-02:** priority considers owner purpose, authoritative time, consequence, evidence quality, dependencies and capacity as distinct dimensions. Reserve useful capacity for genuine exceptions and prevent indefinite starvation across permitted domains. Policies name preemption, wait, coalescing and fairness behavior; no invented emergency, overtime or hiring. The [worked contention/cost rule](07-sovos-master-loop-planning-closure-and-worked-decisions.md), §4, instantiates this requirement through existing owners, showing reservations, safe preemption, infeasible allocation and separately calibrated error costs rather than a new priority store.

**ML-RESOURCE-03:** self-generated events and mirrors retain origin/causal lineage. Repeated no-new-evidence activity is coalesced, deferred or escalated under a bounded policy, not recursively reinjected. Suppression cannot erase a serious independent event. Report affected dropped/deferred coverage rather than claim complete sensing.

## 8. Correction, pause, restart and migration

| Change/failure | Required order | Protected distinction |
|---|---|---|
| Source correction or rejected memory | Verify source revision → find dependent pending context/questions → mark stale → re-observe → re-admit affected work | Past effects are history; reversal is separate authority |
| Owner goal/consent change | Attribute exact scope → fence affected future attempts → reconcile running/partial effects → revise proposed bindings | Whole-mission halt honored; ordinary steering need not cancel unrelated work |
| Pause / revoke / takeover | Stop affected admission and fence workers/triggers → inspect known/unknown effects → persist receipt → hand back only after fresh reconciliation | Disabling a routine does not cancel a source obligation or erase its watch history |
| Worker loss / lease expiry | Fence old generation → retain failure → inspect side effects → reassign only under actual policy and budget | Old worker cannot settle/mutate after reassignment |
| Scheduler/body/daemon restart | Reconstruct projections from owner records → restore exact instance refs → revalidate sources/grants → reconcile missed events/effects | Replay rebuilds state, never replays consequential mutations |
| Model/prompt/embedding/contract change | Stage revision → regression/compatibility review → invalidate affected caches/index generation → bounded migration | New model cannot silently change active routine semantics or memory eligibility |
| Partial execution / failed compensation | Stop conflicting effects → inspect each step → execute only permitted applicable compensation → verify recovery or escalate | Compensation is not automatic undo or business success |

**ML-CORR-01:** maintain source/recall revision dependencies through existing refs/evidence projections sufficient to find affected pending work. No universal dependency database is implied. If that lookup is incomplete, stop dependent effects and expose uncertain coverage; do not assume no impact.

**ML-RECOVER-01:** state changes must reject stale expected revision or generation. Each step preserves pending intent, current disposition and terminal receipt under its owner. Cross-product projection updates are reconciled explicitly; a failed downstream write cannot turn partial state into completed success.

## 9. Receiver proof, closure and reciprocal memory

**ML-OUT-01:** predeclare exact output and receiver postconditions, evidence sources, freshness, verifier role/independence, disagreement rules and terminal dispositions. An executor can offer evidence; it cannot settle its own desired business outcome by narrative. Unknown/partial/disputed/failed states survive every projection.

**ML-OUT-02:** workflow completion requires all mandatory branches and required recovery/compensation terminally settled under policy, not simply one receipt per currently known dispatch. Preserve each attempt's outcome, generation, acceptance decision and evidence. Run completion, accepted business outcome and momentum are separately reported.

**ML-OUT-03:** outcome acceptance may lead to a bounded momentum check only where meaningful and owner-aligned. Bind hypothesis, source predicate, evaluation horizon and stop conditions. Unknown momentum remains unknown; it neither erases achieved success nor authorizes endless work. Close on verified outcome/allowed terminal policy, accepted abandonment/supersession or explicit escalation destination.

**ML-MEM-01:** follow [Master Loop §11.1](02-sovos-master-loop-draft.md) and the [memory-agent handoff](04-sovos-master-loop-source-and-integration-register.md). Submit minimal reviewable episodes/corrections through existing owners; distinguish review acceptance, enqueue, provider receipt, eligible recall and actual use. No automatic promotion of transcripts, model agreement or raw telemetry.

**ML-MEM-02:** later recall rechecks current source eligibility, provider binding, purpose/role, retention, source revision and live work status. Rejection/supersession/erasure defeats stale provider history. Forgetting a memory cannot close an obligation. Native V1 transition, primary-loop maintenance, transcript ownership and cross-host writer qualification remain separate gates; this connection does not activate native writes.

**ML-MEM-03:** test actual reciprocal contribution using the annex's history/feedback controls. Link used recall/policy revisions to independently accepted results, including rejected hypotheses and failed/censored attempts. Do not feed post-outcome evaluation answers into earlier decisions or copy private episodes into portable doctrine.

## 10. Health, useful capacity and explanation

**ML-HEALTH-01:** expose a bounded per-concern coverage/posture: sources known/unknown/stale/denied; watcher health; actual responsibility; model/worker availability; pending effects; current permission; receiver proof and next check. It is a projection of owner records, not another all-seeing system. No available evidence means no clean-health claim.

**ML-HEALTH-02:** select recovery from current source-qualified runbooks within granted targets. An outage does not create permission for a new daemon, provider, credential, customer binding or external disclosure. Independent authorized lanes may proceed; record what remains unobserved.

**ML-VALUE-01:** measure total owner/staff review, coordination and maintenance effort alongside accepted outcomes, operating cost, misses, duplicates, interruptions and recovery. Compare matched before/after/control windows; label estimates and confounding, avoid counting copied evidence or shared gains twice. Faster execution with more human supervision is not automatically capacity returned.

**ML-VALUE-02:** released capacity remains the owner's. Do not refill it with tasks, manufacture reminders or infer higher purpose. Healthy quiet is a valid state. Routine retirement preserves required history and source obligations while removing obsolete triggers/access under their owners.

**ML-EXPLAIN-01:** conversation, API, trusted UI and mobile/voice should explain the same current source-backed concern: what changed, evidence/uncertainty, current responsible actor, permitted next move, why human input is actually needed, and proof still missing. Unknown/unsupported controls render unavailable. Headless operation and safe recovery must not depend on the GUI or optional W.I.N.S./federation.

## 11. Whole Workstream, full Trajectory and Focusa core integration

Owning basis: [issue #618](https://github.com/Startempire-Wire/focusa/issues/618), the [cohesive project journey](https://github.com/Startempire-Wire/focusa/blob/b10c605e1e0ccbdb43d9650945adde7a87fec25d/docs/agent/02-focusa-cohesive-project-flow.md), Specs 102/143/164, Workset Flow Ledger 149, CallGraph 155, proposal-to-settlement 136, ontology 135F, reflex 97 and secondary cognition 78. Exact file/title/version matters: some numerical spec prefixes are reused for unrelated documents. References are owner contracts, not proof every installed operation is available.

### 11.1 Not a task-only integration

```text
owner purpose / accepted portfolio outcome
        ↕ source-qualified links, not a second goal hierarchy
Focusa Project / governed scope
        ↔ coherent Workstream continuity and ownership
        ↔ HLT → distinct MLG branches → STGs → waypoints
        ↔ pinned specifications / acceptance / observed state / gaps
        ↔ Workset requirement membership and completion contracts
        ↔ CallGraphs: dependencies, branches, joins, recovery, frontier
        ↔ exact bounded Workpoints and current admitted attempts
        ↔ actual executors / workers / human handoffs
        ↔ evidence → independent verification → completion / settlement
        ↔ reassessed state/gaps/coverage → next eligible work
        ↔ Wirebot concern/Perpetua/memory/leverage projections
```

This is an integration map, NOT strict nesting of every object. A Workstream is a coherent continuing effort; cross-cutting work may serve multiple goals/Worksets through explicit typed links. Worksets account for admitted requirements and acceptance, CallGraphs for executable dependencies/readiness/recovery, and Workpoints for immediate bounded continuation. Do not duplicate a task to make a diagram a tree. HLT remains project-grounded and cannot be regenerated merely by a new session, body or continuity lineage.

**ML-WS-01:** map each accepted routine/concern requiring governed work to the exact existing project/scope and Workstream, specification/acceptance revision and relevant goal/waypoint refs. Use supported identity/attachment/Genesis mechanisms only when genuinely needed. Do not create a project or always-on agent per alarm, borrow a similar mission, or promote a model-inferred portfolio goal to HLT. Read-only observations and externally owned human work can remain source records until an actual governed assignment is necessary.

**ML-WS-02:** retain both the whole accepted outcome and nearest bounded action. An alarm may expose a new dependency or gap; route it as evidence and a proposed affected-scope refinement, not an automatic replacement HLT. Each admitted action must link upward to acceptance and each required outcome must link downward to justified work or an explicit owned unresolved requirement. During this paper-only phase these are design links, not newly admitted Worksets/Tasks/CallGraphs.

### 11.2 Full, Medium and Short projections

| Projection | Must retain | Invalid substitution |
|---|---|---|
| Full | Complete accepted-outcome coverage, required goal branches/waypoints, specification/acceptance, dependencies, completed/active/blocked/unmapped requirements, linked work/graphs and proof | One active path, a roadmap, a valid graph or the last completed task labeled the full mission |

### 11.3 One progression loop and mandatory return paths

Use #618's **Prepare → Act → Reconcile → Advance** responsibilities through existing owners, not four new states or a second supervisor.

| Move | Master Loop contribution | Focusa/source contribution and required return |
|---|---|---|
| Prepare | Qualified observations, expectations, current owner purpose, incumbent work/capacity and bounded proposed changes | Reuse valid project/Trajectory/spec/Workset/graph/context records; verify the current gap and action bindings or expose owned refinement |

| Reconcile | Observe independent receiver/source state, correction, unavailable coverage and memory relevance | Record candidate evidence; verify acceptance; settle through the owning authority; update observed state/gap and affected dependencies |
| Advance | Project current concern, responsibility, next check and useful capacity to the owner | Select updated valid frontier: act, refine, bounded wait/block, or accepted whole-outcome settlement; independent authorized branches continue |

**ML-WS-04:** a receipt must return through verification/settlement to current-state/gap assessment and dependency selection. Merely linking evidence cannot leave the Trajectory describing pre-effect reality. Missing/untrusted proof creates an explicit gap. A failed/blocked branch does not stop unrelated admitted work; completion of one Workpoint cannot settle the whole Workstream/project.

**ML-WS-05:** daemon/executor continuation must survive chat/model absence, compaction, restart and body change without asking for routine “continue.” Reuse valid unchanged routes; refine only affected dependencies. Pending feedback/unknown effects remain durable under their owners. Pause/revoke stops at the affected boundary immediately, not after finishing a lap. No self-renewed budget or invented work after real acceptance.

**ML-WS-06:** distinguish a finite accepted outcome from a continuing operating service. A recurring routine can remain active after one case closes; rolling/provider-stream Worksets need explicit epoch/admission/sealing policy. Empty current queues, one completed epoch or one successful reminder do not prove a business is finished. Conversely, unrelated backlog cannot prevent settlement of fully satisfied scoped acceptance.

Review gates:

1. **Boundary:** finite sources/products/concerns included, explicit exclusions and historical/unknown regions; preserve the whole-organism purpose.
2. **Conceptual closure:** accepted responsibility allocation; precise object/clock/authority distinctions; each nonterminal state has a current owner and next event/check or honest blocker.

4. **Fault closure:** fixtures cover duplicates, missing/late events, contradictory sources, stale/foreign inputs, model/worker/source loss, partial effects, pause/correction, restart, migration and incomplete acceptance.
5. **Evidence closure:** proof sources, independent acceptance, performance/resource/error-cost policy, migration and rollback are defined; prior passing reference tests are not new runtime evidence.
6. **Owner review:** remaining consequential proposals are accepted/amended/excluded; only then establish decomposition and implementation scope through the existing work system.
