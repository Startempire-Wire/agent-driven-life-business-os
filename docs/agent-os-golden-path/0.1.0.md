# Agent OS Golden Path 0.1.0

- **Status:** `candidate`
- **Date:** 2026-09-08
- **Scope:** portable deployment/build/operations doctrine
- **Parent contract:** repository `AGENTS.md` / Owner Authority Constitution
- **Reference implementation family:** Startempire / Wirebot / Focusa / UIAI Engine / Veragensia / OpenClaw

## 0. Intent

This candidate adapts the useful structural idea behind `burcs.dev/starter` into the Agent-Driven Life & Business OS:

> Build an end-to-end path that an authorized agent can execute from environment identity through production operation, with exact implementation guidance, objective checks, known gotchas, recovery, and explicit exit conditions at every phase.

The source idea is a **method**, not a technology prescription. Cloudflare Workers, D1, KV, R2, Durable Objects, Stripe, or any other source-stack component is adopted only when it is actually the best fit for a deployment.

The target outcome is an OS installation that increasingly **explains and operates itself** to an authorized agent.

---

# Design law

## A. One source of truth per kind of data

Every material state class MUST have an identified canonical owner before new storage or synchronization is introduced.

Classify every store or representation as exactly one primary role:

| Class | Meaning |
|---|---|
| `CANONICAL` | authoritative state for the named domain |
| `DERIVED` | reproducible projection from canonical state |
| `CACHE` | disposable performance copy with freshness/invalidation rules |
| `INDEX` | search/retrieval representation that never silently becomes truth |
| `COORDINATION` | leases, queues, locks, schedules, transient workflow state |
| `EVIDENCE` | immutable/append-oriented proof or provenance about events/outcomes |
| `EPHEMERAL` | runtime-only state safe to lose or rebuild |

If two systems both claim canonical ownership of the same fact class, the phase is not complete until the conflict is resolved or explicitly bounded by domain/scope.

## B. Allowlist surfaces and authority

Public assets, APIs, agent tools, filesystem areas, network destinations, cross-tenant routes, and mutation capabilities should be intentionally exposed. Absence from a denylist is not permission.

## C. Staging/proving route from the start

Every consequential deployment profile defines where changes can be exercised before production. The proving environment may be staging, a disposable tenant, an isolated worktree/container, a preview deployment, or another bounded equivalent. The exact substrate is replaceable; the invariant is not.

## D. Version config; protect secrets

Commit or otherwise version reconstructable non-secret configuration where appropriate. Never commit credentials, recovery codes, private customer context, session tokens, or secret-bearing generated artifacts.

## E. Boring beats clever

Prefer the simplest inspectable mechanism that satisfies the actual invariant. Avoid frameworks that duplicate existing capability. Separate concerns when separation improves failure isolation, observability, replacement, or recovery.

## F. Agents are users/operators now

A mature deployment exposes machine-readable information sufficient for an authorized agent to discover identity, health, capabilities, permissions, scope, documentation, failure semantics, and recovery without depending on undocumented human memory.

## G. No proof theater

Checks must answer whether meaningful behavior works. Do not create elaborate proof pipelines that consume more effort than the outcome warrants. Evidence is proportional to consequence.

Every phase SHALL eventually provide:

IMPLEMENTATION

For `0.1.0`, implementation bullets are portable requirements and reference mappings, not claims about any particular live server.

# Phase 0 — Identity, owner, profile and naming

## Purpose

Establish exactly **whose system this is, which deployment is being operated, what environment it is, and which profile is intended** before creating state.

## Invariants

- Canonical Owner Principal is resolved through the repository authority constitution.
- Deployment identity is stable and unambiguous.
- Environment is explicit: e.g. development, staging, production, recovery.
- Customer/tenant identity is not inferred from hostname, Linux user, model name, or directory alone.
- Domain/name availability checks do not mutate infrastructure unless authorized.

## Implementation direction

A deployment manifest should eventually be able to express, directly or by references:

```yaml
deployment_id: <stable id>
owner_principal_ref: <owner manifest ref>
profile: <reference|sovereign-customer|shared-tenant|other>
environment: <dev|staging|production|recovery>
tenant_ref: <optional>
project_scope: <optional>
domains: {}
```

This example is illustrative, not yet a canonical schema.

## Check

An agent can answer without guessing:

1. Who owns the architecture?
2. Which exact deployment am I operating?
3. What environment is this?
4. What profile applies?
5. What actions are currently authorized?

## Gotchas

- Hostname or service-account identity is often mistaken for authority.
- Cloned customer environments may retain stale owner/tenant defaults.
- A domain being configured does not prove it resolves or serves the intended environment.

## Recovery / rollback

Fail closed on architecture mutation if owner/deployment identity is unresolved. Continue read-only discovery where useful.

## Exit condition

Owner, deployment, environment, and profile resolve to authoritative references.

# Phase 1 — Scaffold and environment baseline

## Purpose

Create or verify the smallest predictable skeleton in which the OS can operate.

## Invariants

- Directory/service ownership is explicit.
- Runtime and source locations are discoverable.
- No private/customer material is copied from a reference deployment by default.
- Re-running scaffold operations is safe or has explicit duplicate protection.
- Existing environment is inspected before creation.

## Implementation direction

Reconcile before adding:

- operating-system/service identities;
- repositories/workspaces;
- state roots;
- runtime configuration roots;
- logs;
- secret injection path;
- service manager/container runtime;
- task/issue system;
- Agent-KB or equivalent operational knowledge surface.

Reference implementations may use existing Wirebot provisioning and Agent Computer profiles rather than inventing another installer.

## Check

A fresh authorized agent can locate source, state, config, logs, secret references, runtime services, and operating docs from bounded discovery.

## Gotchas

- Creating directories before provisioning logic may trigger "already exists" shortcuts that skip personalization.
- Docs frequently describe a historical path after runtime has moved.
- Source checkout success is not service readiness.

## Recovery / rollback

Scaffold operations should be idempotent or leave enough provenance to distinguish pre-existing from newly created resources.

## Exit condition

The environment skeleton is known, bounded, and reproducible without importing another deployment's private identity/state.

# Phase 2 — State ownership and canonical stores

## Purpose

Prevent the most expensive architecture failure: multiple systems silently believing they own the same truth.

## Invariants

Every material state class has:

- domain;
- canonical owner;
- scope key (owner/tenant/project/workstream/etc.);
- consistency expectation;
- mutation authority;
- backup/recovery semantics;
- projection/cache/index consumers.

## Implementation direction

Inventory at least:

- owner/tenant/account identity;
- project/mission/work state;
- business/domain records;
- memory/context;
- conversation/audit;
- task/queue state;
- agent/runtime sessions;
- evidence/receipts;
- credentials/secrets metadata;
- files/artifacts;
- licensing/entitlements;
- observability data.

For the Startempire reference family, explicitly reconcile Focusa, Context Core, Agent-KB, OpenClaw state, memory systems, Beads/task state, WINS/evidence, UIAI evidence, customer provisioning, and any business-system truth rather than assuming one database should own all of them.

## Check

Produce a state ownership table where no row has ambiguous canonical ownership.

## Gotchas

- Search/index systems are frequently promoted into authority accidentally.
- Conversation history can become de facto memory without promotion rules.
- "Latest write wins" hides semantic ownership conflicts.
- Eventual-consistency stores should not service operations requiring read-after-write truth.

## Recovery / rollback

If canonical ownership is ambiguous, freeze conflicting new writers before attempting a migration. Preserve provenance; do not destructively merge stores based on guesswork.

## Exit condition

Every material state class has one canonical owner per exact domain/scope and all replicas have named roles.

# Phase 3 — Derived state, cache, indexes and freshness

## Purpose

Make fast context and retrieval safe without letting stale copies masquerade as truth.

## Invariants

- Cache/index/derived state names its canonical source.
- Freshness is machine-readable where consequential.
- Invalidations happen from the writer/change source when practical.
- Sensitive personalized data is not cached publicly.
- Stale-but-usable behavior is explicit and visible.

## Implementation direction

For each derived representation define:

```text
source
scope
freshness timestamp/digest
invalidation trigger
maximum tolerated staleness
fallback behavior
rebuild path
```

## Check

Change canonical state in a bounded test and verify important consumers converge within the documented tolerance or correctly report stale/degraded state.

## Gotchas

- TTL-only invalidation can leave high-consequence writes stale longer than expected.
- Deploys can repopulate old values after a new writer succeeds.
- "No data" and "fresh empty data" are not equivalent.

## Recovery / rollback

Derived state should be disposable/rebuildable unless explicitly documented otherwise.

## Exit condition

Critical projections cannot silently present stale/foreign state as current truth.

# Phase 4 — Human/agent identity, auth, sessions and tenancy

## Purpose

Bind humans and agents to exact principals, sessions, tenants, and permissions without mixing authentication with architecture authority.

## Invariants

- Authentication proves a principal or credential relationship; it does not mint architecture authority.
- Agent identities are explicit and scope-bound.
- Tenant/session ownership is checked on every private operation.
- Logout/revocation takes effect predictably.
- CSRF/origin/replay protections apply where relevant.
- No sovereign/global fallback for unknown customer context.

## Implementation direction

Reconcile:

- human login/SSO;
- machine/workload identity;
- agent principal identity;
- session stores;
- tenant/workspace routing;
- pairing/device identity;
- authorization and delegated capability checks;
- revocation.

## Check

Use at least two synthetic principals/tenants and prove they cannot read, mutate, reuse sessions, or execute inside each other's private scope.

## Gotchas

- Equal numeric IDs in separate systems do not imply the same principal.
- Admin tier is not necessarily sovereign/operator ownership.
- Session reuse without ownership checks is a cross-tenant leak.

## Recovery / rollback

Unknown or mismatched scope fails closed for private mutation/execution. Recovery should preserve user data while revoking access where needed.

## Exit condition

Exact principal → session → tenant/workspace → capability binding is enforceable and tested.

# Phase 5 — Agent runtime and execution surfaces

## Purpose

Provide replaceable reasoning/execution runtimes while preserving project, authority, evidence, and isolation semantics.

## Invariants

- Runtime/model identity is not architecture authority.
- Chief-of-Staff, project Foreman/orchestrator, and worker roles remain distinguishable where the deployment uses them.
- Project-specific execution resolves exact project/workstream scope before mutation.
- Customer workers do not fall back into a sovereign/global operator runtime.
- Browser/computer actuation follows the same authority/evidence rules as API/CLI work.
- Worker/harness replacement does not erase canonical continuity.

## Implementation direction

Reconcile available:

- OpenClaw or equivalent gateway;
- Wirebot/Chief-of-Staff role;
- Focusa project/Workstream/Foreman surfaces;
- Pi and other build-agent harnesses;
- UIAI/Veragensia computer/browser execution;
- queues/Flow Mesh/CallGraphs/Beads;
- model providers and failover;
- isolation substrate (process/container/VM/worktree/sandbox as appropriate).

## Check

A replacement worker can receive a bounded assignment, locate necessary context/tools, perform one authorized real action, return structured evidence, and leave durable continuity without inheriting unrelated private state.

## Gotchas

- Local workspace creation is not remote agent registration/readiness.
- Tool presence does not mean capability is authorized.
- Shared host/process isolation may be weaker than tenant semantics assume.

## Recovery / rollback

A worker/process can die and be replaced without losing canonical mission/work state. Runtime failure does not produce a false "ready" or "complete" state.

## Exit condition

At least one governed end-to-end worker path operates inside exact scope with recoverable continuity.

# Phase 6 — Network, domains, staging and production routes

## Purpose

Make access paths explicit, separated, testable, and recoverable.

## Invariants

- Production and staging/proving routes are distinguishable.
- Private control planes are not exposed merely for convenience.
- DNS/tunnel/proxy configuration identifies the intended backend.
- TLS/auth boundary is explicit.
- Route creation is idempotent where practical.

## Implementation direction

Reference deployments may use Cloudflare, Tailscale, tunnels, reverse proxies, direct private networking, or equivalents. Preserve the separation of user-facing app, API, and control/agent surfaces when it reduces risk and ambiguity.

## Check

Resolve and request every intended endpoint from the appropriate network position, verify the expected service/environment/identity, and verify unintended/private routes are unavailable to unauthorized callers.

## Gotchas

- A 200 can come from the wrong environment.
- Tunnel configuration can survive while the local service is dead.
- Staging can accidentally become indexable/public.

## Recovery / rollback

Maintain a known route rollback and a private/admin access path appropriate to the deployment.

## Exit condition

The deployment's network surface is intentional and its staging/production distinction is proven.

# Phase 7 — Human + machine discovery and documentation

## Purpose

Make the installation understandable without undocumented tribal knowledge.

## Invariants

- Human docs and machine discovery derive from canonical sources where possible.
- Runtime facts expose freshness/version/provenance.
- Private identities/secrets are not published in public metadata.
- Documentation does not claim deployed behavior without evidence.

## Implementation direction

Provide a bounded orientation path covering:

- deployment identity/profile;
- architecture map;
- service inventory;
- state ownership;
- operating commands;
- health;
- troubleshooting/recovery;
- capability discovery;
- version/freshness.

Use Agent-KB or equivalent for deep operational knowledge rather than forcing every agent to preload an encyclopedia.

## Check

A fresh authorized agent can orient to the installation from a documented/machine-discoverable entry point without asking a human for paths or hidden service names.

## Gotchas

- Huge `AGENTS.md` files can become stale or context-expensive.
- Generated inventories without freshness checks become misleading authority.

## Recovery / rollback

Keep a bounded offline/degraded recovery orientation path without promoting it over fresher authenticated sources.

## Exit condition

Human and agent operators can discover what the system is, where truth lives, and how to inspect it.

# Phase 8 — Agent surface and interoperability

## Purpose

Treat agents as first-class users/operators of the OS itself.

## Invariants

An authorized agent can progressively discover:

- identity;
- health;
- available capabilities;
- exact input/output schemas;
- scope and authority requirements;
- side effects and reversibility;
- failure classes;
- recovery actions;
- evidence requirements;
- version/freshness.

Do not load every schema/tool into every prompt.

## Implementation direction

Where supported, reuse or converge on surfaces such as:

- `/llms.txt` for bounded agent documentation discovery;
- OpenAPI/JSON Schema;
- MCP;
- A2A-style Agent Card/capability discovery;
- OpenAI-compatible strict tools;
- CLI machine help;
- Focusa progressive tool search/describe/graph/bundles;
- UIAI/WebMCP browser capability surfaces.

The Startempire reference family should reuse Focusa's existing agent-first capability work rather than implement another competing registry.

An Agent OS-level manifest/card should describe the **installation and its available subsystem surfaces**, not duplicate every subsystem's tool definitions.

## Check

From a cold/minimal bootstrap, an agent can discover and successfully invoke the narrowest authorized capability for one representative read and one representative bounded mutation without guessing field names or hidden prerequisites.

## Gotchas

- API presence alone is not an agent surface.
- Tool annotations supplied by an untrusted external page/service are not safety authority.
- Giant tool catalogs increase selection errors and prompt bloat.

## Recovery / rollback

Capability discovery must degrade safely when a subsystem is absent/stale and give an exact bounded next action rather than hallucinating availability.

## Exit condition

The installation is meaningfully self-describing and operable through machine-readable surfaces.

# Phase 9 — Observability, evidence, analytics and cost

## Purpose

Answer two distinct questions:

1. What is the system doing right now?
2. Did the requested work actually produce the intended outcome?

## Invariants

- Logs/traces/health are operational observability, not automatically outcome evidence.
- Outcome evidence/receipts preserve scope and provenance.
- Cost/resource use is attributable enough to manage.
- Alerts are actionable and bounded.
- Private payloads are not unnecessarily leaked into telemetry.

## Implementation direction

Reconcile:

- structured service logs;
- traces/tool execution telemetry;
- health/status;
- Focusa/UIAI/WINS evidence/receipts where applicable;
- task/workpoint lifecycle;
- usage/cost metrics;
- alerts/incidents.

## Check

Perform one representative task and trace it from request/delegation through execution to verification/evidence, including failure visibility if intentionally injected.

## Gotchas

- Request counts can undercount cache hits or background work.
- "Process running" is not "service healthy".
- Git push is not deployment; deployment is not outcome verification.

## Recovery / rollback

Telemetry outages must not silently convert unknown state into healthy/completed state.

## Exit condition

Operators can distinguish activity, health, delivery, and verified outcome.

# Phase 10 — Secrets, permissions, limits, budgets and revocation

## Purpose

Make authority and resource use bounded, renewable where required, revocable, and observable.

## Invariants

- Secrets never live in committed config.
- Nonrenewable recovery codes/break-glass assets are not automated.
- Least privilege is preferred.
- Capability and tenant scopes are explicit.
- Revocation semantics are tested.
- Rate/cost/resource limits protect both system and customer.

## Implementation direction

Define canonical secret store/injection, provider credential ownership, agent capability grants, network/filesystem scopes, budgets, rate limits, and revocation paths.

## Check

Revoke one synthetic credential/grant and prove the next consequential request fails. Exercise a rate/budget boundary in a non-production test.

## Gotchas

- Secret values can leak through argv, logs, child errors, generated config, or frontend assets.
- Stale long-lived sessions can outlive account revocation.

## Recovery / rollback

Support rotation/re-issuance without requiring finite recovery assets.

## Exit condition

Secrets and authority can be granted, observed, limited, rotated, and revoked predictably.

# Phase 11 — Entitlements, licensing, billing and BYOK

## Purpose

Bind commercial/product entitlement to operational capability without confusing payment state with owner authority.

## Invariants

- Entitlement state has a canonical owner.
- Payment webhook/API success is acknowledged and idempotent.
- Customer runtime readiness is distinct from billing success.
- BYOK/provider-key ownership is explicit where supported.
- Downgrade/suspension preserves data according to policy.

## Implementation direction

This phase is optional for purely personal/self-hosted profiles. Commercial profiles reconcile licenses, subscription/tier, provisioning lifecycle, provider keys, and restoration/offboarding.

## Check

Synthetic lifecycle tests cover create/upgrade/downgrade/suspend/reactivate/revoke as applicable without mutating real customer accounts.

## Gotchas

- HTTP success can contain a semantically wrong tenant/account response.
- Billing events replay and arrive out of order.
- Account cancellation should not silently delete durable customer data.

## Recovery / rollback

Lifecycle operations are retry-safe and preserve identity/data lineage.

## Exit condition

Commercial entitlement changes settle only after acknowledged downstream effects and never falsely imply runtime readiness.

# Phase 12 — Tests, migration, CI/CD, deploy, rollback and repair

## Purpose

Create a path from source/config change to verified installed behavior without using production as the test harness.

## Invariants

- External data parsers have fixtures/replay where worthwhile.
- Schema/data changes are migrations, not ad hoc production edits.
- Staging/proving deployment precedes consequential production rollout.
- Build/deploy scripts fail closed rather than print false success.
- Rollback/repair is part of the path.
- Deployment proof names the installed revision/config when possible.

## Implementation direction

Use the native CI/test/deploy mechanisms of each subsystem. The Golden Path coordinates acceptance; it does not require one monolithic CI pipeline.

A future executable orchestrator should call existing authoritative test/deploy/doctor capabilities rather than reimplement them.

## Check

For a bounded change:

```text
source/config change
→ tests/build
→ isolated/staging deploy
→ smoke/behavior check
→ production deploy if authorized
→ installed revision verification
→ outcome/receipt verification where required
```

## Gotchas

- Build scripts can hide failed frontend/tool steps.
- GitHub CI green does not prove a deployment occurred.
- A source migration can pass while the deployed consumer still expects an older contract.

## Recovery / rollback

Every material migration/deployment defines rollback or forward-repair behavior and preserves evidence needed to diagnose failure.

## Exit condition

The system has a repeatable delivery path with truthful stage boundaries.

---

# Phase 13 — Launch, acceptance, handoff and ongoing operation

## Purpose

Prove that the intended human/business operator can actually use the system and that the next agent can maintain it.

## Invariants

- Acceptance is end-to-end, not component-by-component only.
- Customer/private profile tests use authorized identities/data.
- Known degraded state is disclosed.
- Operating ownership and escalation are explicit.
- First-day/first-week observation is proportionate to consequence.

## Implementation direction

Acceptance should cover relevant profile functions such as:

- human login/interface;
- agent/Chief-of-Staff interaction;
- project/Foreman routing;
- browser/computer action;
- memory/context retrieval;
- evidence/receipt visibility;
- customer isolation;
- restart/recovery;
- backup/restore expectations;
- handoff to a replacement agent/operator.

## Check

Run one real representative outcome end-to-end in the intended environment and verify the user-facing result plus the operational/evidence path behind it.

## Gotchas

- A technically healthy backend can still have a broken user flow.
- Provisioning success often precedes memory/agent/tool readiness.
- A beautiful dashboard can hide missing execution binding.

## Recovery / rollback

The deployment has a documented and tested route to diagnose, pause/revoke, restore, and resume without relying on the original builder's memory.

## Exit condition

The deployment is accepted as working in named scope, and a replacement authorized operator/agent can maintain it from durable system knowledge.

# Portable profile model

The Golden Path should support profiles without fragmenting the core contract.

Initial profile concepts:

```text
reference-sovereign
  full owner-controlled reference environment

sovereign-customer
  dedicated customer runtime/data/network/secret boundary

shared-tenant
  explicitly isolated tenant/workspace over shared infrastructure

personal-life
  individual deployment emphasizing ambient/context/personal systems
```

These are candidate labels. The server reconciliation may find better canonical profile names already present in provisioning/runtime code. Reuse those names if they exist.

Each profile should declare phase applicability, required capabilities, stronger constraints, and acceptable evidence — not duplicate the entire Golden Path.

# Increasing executability

The end state is not a larger Markdown file. The end state is a progressively executable contract.

Candidate lifecycle:

```text
inspect
→ reconcile
→ plan only genuine gaps
→ provision/configure
→ verify each phase
→ doctor degraded phases
→ repair
→ publish evidence + next version lessons
```

Before adding a new `agent-os` binary or service, the server agent MUST inventory existing CLIs, APIs, provisioning scripts, Focusa tools, Agent-KB, Wirebot `wb`, UIAI, Veragensia, OpenClaw, and task mechanisms. A thin adapter over existing capabilities is preferable to a parallel platform.

# 0.1.0 acceptance

This version is intentionally a **portable candidate prepared outside the live server**. It becomes useful through server-side reconciliation.

The next server iteration must:

1. map each phase to real current components;
2. classify each important store using the state taxonomy;
3. identify contradictions/stale docs without copying private data here;
4. identify which checks already exist;
5. find the smallest missing executable slice with disproportionate leverage;
6. implement and verify that slice in the appropriate operational repo/environment;
7. record real gotchas and recovery lessons;
8. publish the portable improvements as the next Golden Path version;
9. keep deployment-specific facts in Agent-KB/runtime authority rather than freezing them into this portable contract.

Use [`SERVER_AGENT_HANDOFF.md`](./SERVER_AGENT_HANDOFF.md) as the execution prompt.
