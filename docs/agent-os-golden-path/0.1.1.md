## 1. What this revision proves

The upstream candidate and handoff have been pulled and reviewed, and the public starter reference has been inspected. This revision addresses ambiguities found in that review. It does **not** claim a reconciled live estate, new executable capability, installed release, customer rollout or complete end-to-end acceptance.

The [server handoff](SERVER_AGENT_HANDOFF.md) still requires live reconciliation, one implemented and verified high-leverage slice, and a subsequent evidence-grounded version. This clarification is not a substitute for those outputs.

## 2. Phase numbers are not permission or a blind execution schedule

Retain phases 0–13 as coverage labels. Derive actual execution dependencies from the selected deployment and existing operation contracts. Owner/scope resolution, renewable authentication, required licensing, budgets, safe proving and evidence collection apply **before the action that needs them**, even when their detailed chapter occurs later.

In particular:

- Phase 10 controls do not wait until runtimes and routes have already been changed.
- Phase 9 receipt/failure visibility begins with consequential operations, not after setup.
- Phase 6's safe proving route exists before the first consequential deployment, not only after runtime installation.
- Phase 4 authorization/isolation applies before private access; a late two-tenant test cannot retroactively authorize earlier access.
- Phase 11's optional commercial billing does not make a required subsystem license optional in a personal deployment.
- Phase 7 orientation and Phase 8 discovery are used from the start to locate canonical instructions and operations; do not fabricate their prerequisites.

On a genuinely fresh environment, locate the existing owner-authorized bootstrap/install path first. If it cannot establish the required control plane, record that specific bootstrap gap; do not invent a bypass or require the not-yet-installed daemon to authorize its own installation. The contract does not grant general shell-based operation outside an explicitly authorized bootstrap/recovery path.

## 3. Distinguish setup mode from deployment profile

Reuse the canonical profile names found in existing provisioning rather than treating the base's illustrative labels as a new schema. Separately select the intended operation:

| Mode | Required distinction |
|---|---|
| Inspect | Read-only inventory and disposition; no provisioning side effects. |
| Fresh setup | Exact authorized destination; no inherited owner credentials or customer data; verify every required prerequisite. |
| Adopt partial setup | Inspect actual resources and ownership before creating anything; preserve pre-existing state and record what is reused. |
| Repair | Restore a named broken condition under existing authority; retain incident evidence and unaffected state. |
| Upgrade | Prove compatibility, migration/replay behavior, rollout destination and rollback/forward repair before replacing installed behavior. |

Repeated and interrupted runs must distinguish pre-existing resources, confirmed newly created resources and uncertain side effects. Reconcile uncertain writes before retries; do not repeat account creation or provisioning after a response-parsing failure. An unchanged rerun must not duplicate resources or silently reset personalization.

## 4. Close the gap between a phase description and executable setup

Before describing any profile path as executable, bind every applicable phase to the owning system's current interface and evidence. Use existing task/CallGraph and operation contracts; the following is a review checklist, not a new runtime schema or ledger:

- exact deployment/profile/mode and authorized scope;
- required inputs, source of each value, validation and any necessary human consent;
- predecessor conditions and explicit phase applicability;
- canonical owning component and current command/API/tool/schema reference;
- side effects, credential handles, budget/timeout and cancellation behavior;
- idempotency, duplicate detection and handling of uncertain completion;
- observable failure and bounded recovery/rollback;
- expected output and a check through the actual consumer;
- receipt/evidence, installed version where relevant, and replacement-agent continuation.

Do not copy volatile endpoints, secrets or private configuration into this portable candidate. Keep them in the correct deployment knowledge/credential authority and refer to them. Do not invent `agent-os` commands, an aggregate registry, or a universal installer solely to fill these rows.

## 5. Phase applicability and truthful acceptance

Each selected profile must account for all fourteen phases. For review, distinguish:

- **required:** has an implementation gap, is ready, or is blocked; an unknown prerequisite is not a pass;
- **verified:** the named consumer check passed in the exact scope, with sufficiently current evidence;
- **not applicable:** an explicit profile rule explains why the phase is unnecessary.

These dispositions describe the review; they do not replace the canonical runtime's task or readiness states. A failed discovery call, unavailable credential, stale result or absent mandatory component cannot be relabeled "not applicable." A completed optional phase cannot compensate for an unverified mandatory phase.

Full end-to-end acceptance requires more than one healthy component. Demonstrate:

1. A new authorized agent or replacement agent discovers owner, scope, instructions and existing capabilities without hidden setup knowledge.
2. It completes the authorized setup/repair path using the real owning tools, with required dependencies satisfied.
3. The intended Chief-of-Staff/worker performs a meaningful bounded operation and the intended human can observe the correct result.
4. Evidence links the request, execution, installed state and consumer result; denial, failure and cost are visible where consequential.
5. An unchanged rerun and an interrupted/restarted run preserve identity and data, with recovery tested where material.
6. The applicable client profile preserves independent owner/tenant boundaries and revocation while still allowing authorized work.
7. A replacement agent continues from durable references rather than the original session transcript.

A one-slice success supports a **scoped milestone**, not a claim that all profiles or the complete Golden Path work. Publish iterative versions with their exact evidence scope; do not wait for universal perfection or claim it prematurely.

## 6. Adapt the starter's method, not its application defaults

The [starter reference](https://burcs.dev/starter) contributes ordered checks, concrete implementation guidance and production-derived gotchas. Its Cloudflare services, domain purchases, app monetization, public wildcard CORS, telemetry and alert thresholds are not automatic choices for a private Life & Business OS.

For this reference ecosystem, inspect and reuse Wirebot/OpenClaw, Focusa, Agent-KB, UIAI/Veragensia and existing provisioning/domain systems at their actual ownership boundaries. KnownHost remains the current reference Focusa authority; a remote worker or public display is not a second daemon/writer. Client installations establish their own owner and scoped authority rather than inheriting reference identities or credentials.

Instruction files are also setup inputs: verify the authoritative source, deployment copy, native loader and current tool availability separately. An updated Git file does not prove a running agent refreshed; a healthy service does not prove the agent can invoke it. Resolve a source/mirror version conflict rather than choosing the newer-looking file silently.
