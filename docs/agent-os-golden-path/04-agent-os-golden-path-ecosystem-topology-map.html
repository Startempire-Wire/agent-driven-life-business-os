3. Different dimensions—not competing lanes

Use the existing contracts to decide valid combinations. A label in one column does not answer the questions in another.

Purchase / participation

Wirebot Direct or the network bundle. Direct customers need not buy network participation.

Not equivalent to DIY or dedicated infrastructure.

Runtime isolation

Shared or dedicated. The tier/runtime contract describes managed Sovereign as a dedicated runtime boundary.

A personal bot identity does not necessarily mean a separate gateway process or physical machine.

Hosting / operation

Managed infrastructure or client-owned infrastructure; client-owned deployments can remain managed by agreement.

Sovereign does not automatically require self-hosting. Existing deployment and ownership contracts decide.

Federation / sharing

Explicitly agreed collaboration across independently scoped participants. Preserve ownership and consent for what crosses a boundary.

Not blanket access to private memory or client state; current behavior needs its own evidence.

Interface / access

Web, extension, channels, the proposed operated wrapper, or individual components according to actual requirements.

The interface does not determine the deployment mode or grant credential use.

Settled operated offering

$250k flat · five visits · ≤5h each. Any support contract floors at $450k/year.

Wrapped process/app/library: operator IP, structurally tethered to the operated service. Independent components: their own licenses and DIY sovereignty. These terms are unchanged, not universal pricing for every Wirebot tier.

4. Where the diagnostic fits

“Given what this person wants to accomplish, what already exists, what works, and what is actually missing?” Start with the engagement—not the assumption that every machine should contain this server’s toolchain.

  1. Desired outcome
  2. Applicable checks
  3. Observations
  4. Relevant gaps
  5. Existing governed work
  6. Recheck & usable result

Observe without assuming

A requirement may be met locally or remotely, not apply, be blocked, or remain unknown. Match checks to actual network integrations, managed services or deployment needs.

Applicability output not implemented yet

Connect to the right owner

Determine approved report ownership, consumer, identity binding, permissions, retention and readback before production delivery. Reuse the existing subsystem that actually owns the responsibility.

Real intake binding remains open

Explain readiness plainly

Show required capabilities working, blocked and untested. A later percentage needs a meaningful denominator and cannot conceal a critical blocker.

Numerical scoring remains a candidate

Keep these distinct: an observation is not enrollment; a fingerprint is not identity authority; readiness is not business success. Tauri and the relevant existing extension can eventually present the same underlying diagnostic workflow without duplicating the checker or introducing a fleet store.

5. Keep the proven deployment spine

The existing nine-stage sequence remains intact. These are Golden Path stages for an applicable operated engagement—not mandatory infrastructure work for every ecosystem user. Evidence, prerequisites and approved scope determine execution.

  1. Engage

    Engagement, owner authority and consent design.

  2. Workstation substrate

    Applicable agent tooling, Focusa, early UIAI access and secret-safe operation.

  3. Chief of Staff genesis

    Local, git-backed workspace and initial Chief-of-Staff context.

  4. Cloud landing

    Approved control-plane substrate; cloud readiness is not yet CoS relocation.

  5. Mesh + identity

    Approved connectivity, identities and access across the actual estate.

  6. Knowledge + audit

    Document relevant systems, retrieve knowledge and understand business needs.

  7. Chief of Staff ascends

    Relocate the git-backed workspace to the approved cloud-primary operation.

  8. Operating plane

    Voice, recurring tasks, schedules and governed agent roles.

  9. Ongoing operation + handoff

    Support, benefit review, continuity and evidence-backed improvement.

Diagnostics may inform qualification, stage checks and support; running one does not complete the whole spine. Exact stage details and settled constraints remain in the single working doctrine.

6. What exists—and what still needs proof

Historical bounded observations

Useful prototype, limited coverage

  • Ten CLI presence/version checks; three health paths, seven health values not assessed.
  • Linux reference run after KB access repair reported ten present and three healthy.
  • Synthetic missing-tool test returned exit 1. Install mode printed routes without installing.
  • Local HTTP sink accepted a report. Raw machine-id and the tested synthetic bearer were absent from captured output.

These are prior test observations, not fresh runtime verification by this diagram.

Implementation / acceptance gaps

Fine-grained tuning in existing owners

  • UIAI/OpenClaw and remote/applicable capability coverage are missing.
  • Manual JSON interpolation, missing-label looping, flag order and repeated/unbounded checks need hardening.
  • Unhealthy results do not affect the checker exit code; HTTPS is not enforced.
  • A stable hash is linkable, not proof of anonymity or enrollment. Account access does not prove scoped client credentials.
  • Real receiver isolation, retention, receipt/readback, macOS/Windows and client-operated paths remain unproven.

One existing task ledger

Estate, ownership, bindings and run review (GP-04–07): in progress. Bounded prior work is retained; help/list reads do not prove lifecycle behavior. Implementation and verification (GP-08/09): in progress. Full workflow, reproducibility, isolation and handoff/publication (GP-10–13) remain planned.

0.2.0 is a candidate. This update changes documentation and the visual—not scripts, credentials, hosts, public websites, intake infrastructure or enrollment.
